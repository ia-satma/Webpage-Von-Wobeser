## 2. Arquitectura que no debe cambiar

La plataforma continúa siendo un único servidor Express con cuatro superficies:

1. **Sitio público:** el espejo HTML/Joomla guardado en `frontend-mirror/`, transformado en
   cada solicitud por `server/mirror/` con Cheerio y datos de PostgreSQL. No reactivar React
   para páginas públicas.
2. **Administración:** SPA React 18 exclusivamente bajo `/admin/*`.
3. **Backend:** Express, PostgreSQL y Drizzle.
4. **Servicios operativos:** agentes, cola, auditorías, medios y controles de seguridad.

El orden de arranque de `server/index.ts` sigue siendo crítico:

1. Registrar APIs.
2. Registrar el espejo con `setupMirror`.
3. Registrar manejador de errores.
4. Registrar estáticos de producción o Vite de desarrollo.
5. Escuchar el puerto e iniciar después los trabajos secundarios.

No borrar, mover ni “limpiar” `frontend-mirror/`. Si falta la plantilla guardia
`frontend-mirror/index.php/lawyer/l-134.html`, las rutas públicas se deshabilitan y el
catch-all de React puede responder de manera incorrecta.

## 10. Incidentes del 20-ago: causa raíz y resolución

### A. Menú transparente/inoperante en desktop y móvil

**Síntoma observado:** al desplazarse por Inicio, los textos del menú parecían transparentes,
contenido como “Latin Lawyer” o Reconocimientos pasaba sobre la navegación y el desplegable no
recibía clics.

**Causa raíz confirmada:** las plantillas históricas de Inicio no cierran el hero antes de
imprimir el header y nav persistentes. Por ello, al interpretar el HTML, `header.header_JS` y
`nav.nav.menu_JS` quedaban dentro de `.home__hero`. La optimización correcta del video móvil
añadió `overflow: hidden` e `isolation: isolate` al hero; al formar un contexto de apilamiento,
secciones posteriores podían pintar y capturar eventos encima de ese menú anidado.

**Qué no resolvía el problema:** forzar fondo blanco, opacidad o z-index en CSS mejoró la vista
inicial pero no eliminó la jerarquía incorrecta. Por eso las correcciones visuales previas no eran
suficientes.

**Solución definitiva (`16c87c2`):** `renderHome` clona el header y la navegación persistentes,
elimina sus nodos heredados y los reinserta como hijos directos de `body` antes del hero:

    body > header.header_JS
    body > nav.nav.menu_JS
    ... hero y contenido ...

La solución preserva aislamiento, altura y video del hero sin mover el banner rojo ni modificar
contenido administrativo.

**Regresión automática:** usa las plantillas reales ES y EN, comprueba un header y nav directos,
cero cromo persistente dentro del hero, y que la franja roja conserve su posición antes del
contenido posterior. El recorrido local real confirmó, en varios puntos de scroll, menú visible,
opacidad 1, fondo blanco, área de clic superior y sin overflow horizontal.

### B. Banner rojo mal ubicado y testimonial demasiado alto

- El HTML histórico también dejaba una anidación defectuosa alrededor del hero. Se normalizó la
  franja roja como bloque posterior al hero y se protegió su orden con pruebas.
- Una regla heredada de `100vh` hacía excesivo el espacio de testimonios. La capa final
  `vwb-stability.css` sustituye esa altura por contenido natural y padding vertical acotado,
  preservando texto centrado, flechas, Slick y reducción de movimiento.

### C. Página caída por error de pool PostgreSQL

**Síntoma:** Preview/producción mostró “Internal Server Error”; logs de Replit indicaron
`HighWaterMark`, evento `error` en `BoundPool` y traza de pg.

**Causa:** node-postgres emite `error` cuando una conexión ociosa muere por red/base. Un
EventEmitter sin listener trata ese evento como fatal y termina el proceso.

**Solución (`7f49c54`):** `attachDatabasePoolErrorHandler` escucha el evento, registra un
mensaje limitado y saneado (sin URL/contraseña), y permite a pg reemplazar el cliente. Las
solicitudes activas mantienen su manejo normal de error; el proceso no debe caer por una conexión
ociosa.

### D. Replit proponía cambios de base no confiables

- No aceptar SQL generado por la interfaz que contenga `DROP TABLE`, `DROP COLUMN`,
  `CASCADE` o deshabilite RLS sin revisión específica.
- `start:workspace` ejecuta `npm run db:migrate` de forma explícita sólo cuando la base está
  lista. Esto alinea la base de desarrollo con migraciones aditivas antes de Preview y reduce
  propuestas de reversión de Replit.
- Para una base nueva, mantener el flujo seguro de handoff; no ejecutar migraciones genéricas
  sobre una base vacía.

## 14. Procedimiento seguro en Replit

Para actualizar una copia de Replit sin perder una configuración local de `.replit`:

    git stash push -m "replit-local-config-before-<sha>" -- .replit
    git pull --rebase origin main
    npm run build
    npm run dev

Si aparecen otros archivos modificados además de `.replit`, detenerse y revisarlos antes de
rebase. Si existe `.git/index.lock`, confirmar que no hay otro Git activo antes de eliminar
sólo ese lock obsoleto.

Para publicar:

1. Confirmar que el pull llegó al SHA aprobado.
2. Ejecutar build y abrir Preview.
3. Probar Inicio, menú en scroll, una ruta de Abogados, Contacto/mapa y el footer en ES/EN.
4. Revisar logs: errores de CSP necesitan URL/directiva para diagnóstico; 304 de manifest/webmanifest
   son normales.
5. En Publishing, detenerse ante SQL destructivo y no aprobarlo automáticamente.
